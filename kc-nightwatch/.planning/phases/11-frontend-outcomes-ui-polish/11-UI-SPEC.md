## Component Contracts (Phase 11 New/Modified Elements)

### 1. Outcomes Page (`app/frontend/pages/outcomes.ts`) — NEW

**Layout:** Identical split-panel to `runs.ts`. Full-height flex column. Left = filter bar + list. Right = detail panel when an outcome is selected.

**Source decision:** D-01 (list → detail), D-02 (filter bar), D-03 (card fields), D-04 (detail panel)

**Filter bar:** `padding: 12px 16px`, border-bottom, 3 `<select>` dropdowns:
1. Target — "All targets" default, populated from unique targets in outcomes list
2. Type — "All types" | "pr" | "linear_issue"
3. Status — "All statuses" | "open" | "merged" | "closed" | "completed" | "cancelled"

Filter bar style: copy exactly from `runs.ts` lines 202–224.

**Outcome list item:**
- `padding: 12px 16px`, border-bottom, cursor: pointer
- Hover: background var(--panel)
- Selected: no special border (detail panel drives selection feedback)
- Left side: type badge + target name + summary (truncated, max 1 line, text-overflow: ellipsis)
- Right side: status dot (8px circle) + created date string

**Type badge:** 11px, padding 2px 6px, border-radius 4px, background var(--btn-secondary), color var(--muted)
- `pr` → text "PR"
- `linear_issue` → text "Issue"

**Status dot color mapping:**
```
open       → var(--accent)
merged     → var(--success)
completed  → var(--success)
closed     → var(--error)
cancelled  → var(--muted)
```

**Summary truncation:** max 60 characters, `white-space: nowrap`, `overflow: hidden`, `text-overflow: ellipsis`

**Detail panel (right side, when outcome selected):**
- `padding: 16px`, `overflow-y: auto`
- Header: full title (14px, weight 600), `margin-bottom: 16px`
- Fields section: same pattern as target-detail.ts "North star" card
  - `background: var(--panel)`, `border: 1px solid var(--border)`, `border-radius: 6px`, `padding: 12px`
- Field list (label 12px muted 600, value 14px text):
  - Target, Type, Status (with color), Created, Signal ID (monospace 13px), Run ID (monospace 13px)
- URL: `<a href={url} target="_blank">` styled as `color: var(--accent)`, font-size 14px, full URL visible (not truncated)
- Status check button: `padding: 3px 8px`, font-size 12px, `border: 1px solid var(--accent)`, `color: var(--accent)`, background transparent, label "Check status"

**Empty state (no outcomes yet):**
- Heading: "No outcomes recorded yet"
- Body: "Outcomes appear here after a run creates PRs or Linear issues."
- Style: centered in list area, color var(--muted), font-size 13px — copy from `runs.ts` empty state pattern

**Empty state (filter returns no results):**
- "No outcomes match the current filters."

### 6. Target Detail Schedule Section (`app/frontend/components/target-detail.ts`) — MODIFIED

**Source decision:** D-08, D-09

### 7. Add Target Wizard Schedule Step (`app/frontend/components/add-target-wizard.ts`) — MODIFIED

**Source decision:** D-15, D-16

Total steps: 5 (was 4). Step dots: 5 dots.

New step inserted as **Step 4** (before existing Step 4 "Preview + save", which becomes Step 5).

Step 4 content:
- Label: "Schedule (optional)" (12px, muted, 600, margin-bottom 8px)
- Checkbox: "Use global schedule" — default checked
- When unchecked, show interval input:
  - Label: "Run every (hours)" (12px, muted, 600, margin-bottom 4px)
  - `<input type="number" min="0.17" step="1">` — 0.17h ≈ 10min (MIN_SCHEDULE_INTERVAL_HOURS floor)
  - Validation: if value < 0.17, show inline error "Minimum interval is 10 minutes" in var(--error) at 12px
- Validation happens on "Next" click, blocks progress if invalid
- State: `useGlobalSchedule: boolean` (default true), `customIntervalHours: string`

Step validation (all steps):
- Step 1: name required (existing gate, unchanged)
- Step 4: if !useGlobalSchedule && customIntervalHours < 0.17 → block with inline error

### 8. Nav Gap Fix (`app/frontend/app.ts`) — BUG FIX

**Source decision:** D-17

**Root cause (from code inspection):** `app.ts` line 123 uses `padding-bottom: 48px` on the content wrapper to offset the fixed bottom nav. This creates a visible gap/border artifact where the content area padding-bottom collides with the nav's `border-top`.

**Fix:** Change content wrapper from `padding-bottom: 48px` to `margin-bottom: 48px` — OR verify the ScheduleBar bottom border + content area top do not produce a doubled border. Specific fix: remove `padding-bottom: 48px` from the middle `<div>` and instead ensure the `#app` container height calculation is correct. If a visual gap remains after margin fix, check if `bottom-nav.ts` has any `margin-top` on the fixed nav.

**Expected result:** Content scrolls cleanly to the bottom edge of the visible area with no black line visible between the last content item and the nav bar.

## Interaction Contracts

### Polling Behavior

| Component | Poll interval | Condition |
|-----------|--------------|-----------|
| Outcomes page | 60 seconds | always when page is active |
| Outcomes status refresh | on "Check status" click (manual) | user-initiated only |
| Sidebar status dots | driven by existing run poll (5s when active) | unchanged |
| Parallel summary header | driven by existing run poll (5s when active) | unchanged |
| Schedule countdown in target-detail | `setInterval(60_000)` local timer | always when target selected |

Outcomes page uses `usePoll(loadOutcomes, 60_000, true)` — always polls while active (not gated on active runs), because outcome status can change any time.

### Hash Routing

| Route | Page | Sub-routing |
|-------|------|-------------|
| `#/outcomes` | Outcomes list | no sub-id routing needed — detail shown inline in split panel |
| `#/outcomes/:id` | Outcomes detail | optional — set location.hash on row click, read on mount |

Sub-routing is at developer discretion. The list→detail split panel handles selection in-component state (no URL requirement for initial ship).

### Status Check Flow (Outcomes Detail)

1. User clicks "Check status" button
2. Button enters loading state: `disabled`, opacity 0.5, label "Checking..."
3. `GET /api/outcomes/:id/status` — response: `{ status: OutcomeRecord['status'] }`
4. On success: update local status, re-render badge, button returns to normal
5. On error: show toast "Status check failed" via `showToast()` (error variant), button returns to normal

### Wizard Schedule Step Navigation

- "Use global schedule" checked (default) → Next is always enabled
- "Use global schedule" unchecked + valid interval → Next enabled
- "Use global schedule" unchecked + invalid/empty interval → Next disabled, inline error shown below input
