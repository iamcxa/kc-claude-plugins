# Private delivery preparation

Use this checklist with [private-operations.md](private-operations.md), which owns
licensing, credential and recovery instructions. Preparation does not authorize
serving, issue credentials or establish a valid license. The owner handles the
hobby-license application; preserve its watermark and the normal production
build. Do not reuse the earlier development canvas build for retained service.

## Freeze the proposed inputs

Record the candidate commit, package-lock hash, installed runtime/tool versions,
backend/operator bundles and static-asset hashes in the private handback. Compare
application source and the lockfile with the accepted readiness candidate. Keep
provider identities, environment values and saved-version receipts outside Git.

Prepare an empty local Node storage destination and a grant-file path without
starting the server. An empty grant template denies access until deliberately
replaced with fresh per-principal grants. Run the existing server with the private
storage/origin settings; local native clients use its loopback MCP endpoint.
Do not start `npm run canvas` as a retained-license workaround. Any local browser
entry needs the normal licensed production build and the existing session exchange;
there is no new sign-in UI in this delivery.

Copy the existing Cloudflare backend, operator and local-caller examples into the
private handback. Pin their `main` files to the reviewed bundles. The prepared
backend and bridge keep routes, public subdomain and preview URLs disabled, with
no R2 binding. Record the exact proposed backend name and verify its absence before
any future provisioning. A serving proposal may enable only the backend's public
subdomain; private admission still applies. The operator bridge stays private and
the caller stays local. The rollback config disables that backend entry while
preserving namespaces and stored data; namespace deletion is not rollback.

The accepted Sites validation source may contain a former temporary backend and
test-room constants. Preserve it and its served version. Make a new local overlay
that changes only the reviewed backend/room configuration, and prove the remaining
proxy logic unchanged with a mechanical comparison. Build fresh static assets with
the normal production path, preserving the existing route prefix and canvas code.
Neither a successful build nor the latest saved version proves a serving switch.

## Stage and switch after separate approval

1. Obtain the applicable license and independently accept the exact licensed build.
   Resolve the workflow guard disposition described below and approve retained
   serving, host entry and initial data scope. Keep the platform on Free.
2. Recheck the exact provider names, current plan and owner-private Site policy.
   An enabled invite capability is not an existing visitor grant. Capture the
   actually served version, environment key set and original room readback before
   changing anything; do not infer serving state from the newest saved version.
3. Issue fresh finite-lived principal IDs using the existing grant helper. Keep
   agent and local-operator secrets in protected files/environment only. Prepare
   token-free native-client settings, and use a separate Sites principal limited
   to the reviewed rooms. Do not reuse temporary validation credentials.
4. Take a stopped-writer document-plus-policy backup. Prepare a fresh target and
   restore using the existing controls only when the selected data move is
   explicitly authorized. Verify records, capabilities, fresh access and old
   credential denial before changing an entry.
5. Save a new Sites version without changing the served version. Review its exact
   source/build and environment mapping. Then switch only the approved entry and
   perform the bounded post-switch acceptance against the pinned candidate.

These are future actions, not commands to execute during preparation. The private
handback supplies exact paths, configs, native-client settings, saved rollback
receipt and explicit commands for the selected candidate.

## Failure before and after the entry switch

Before the switch, leave the old entry served. Preserve the failed target and
its diagnostics; stop the temporary caller and revoke/remove only newly issued
credentials once no longer required. Keep any target with data quarantined until
its backup and ownership are confirmed.

After the switch, pause writers and back up the failed target before returning
traffic. Restore the recorded prior Site version and prior environment key set;
remove only newly introduced keys. Disable the candidate backend's serving entry
using the saved closed config, preserving its namespaces. Reconcile current
revocations before reopening the old entry. An old snapshot does not include
newly acknowledged work: retain that work for explicit reconciliation. Do not
replace current authorization with an old grant file.

## Number-guard boundary

The adopted generic guard expects numbered SQL migrations at its comparison
base. This product initializes adapter metadata in TypeScript, delegates room
SQLite migrations to its pinned SDK and declares fresh Durable Object classes in
Worker configuration. Those are real persistent-state surfaces, so relabeling the
task or inventing an SQL directory would be false.

Keep the full task-aware guard CONFIG ERROR / NOT PASS. A one-time comparison can
verify unchanged initialization source, locked SDK and namespace declarations,
accurate applied-commit accounting and the reserved architecture record. This is
supplemental evidence, not a replacement PASS or an automatic waiver. The owner
must choose a task-scoped exception for this unchanged delivery or defer delivery
until appropriate workflow tooling exists; that tooling is a separate change.
