S13我知道目前比的是哪個來源

分別列出每runtime的CLI package／core／contract、已配置的code／ADR checkout與實際loaded view；每個data repo各報commit、digest、觀測時間。已安裝package無code Git checkout時報package version及不適用，不假造Git最新；選配host另列，不是CLI前提。

S14我看懂一致落後領先分岔或未知

相同repo/ref、可讀遠端目標與完整祖先證據才判checkout一致／落後／領先／分岔；不足為remote unknown並附observed_at。每runtime loaded view依實際data commit回報，不把code已更新或舊tracking ref當資料最新；沒有checkout是不適用，source mismatch另報。

S27我知道更新被哪些本機狀態阻擋

先由 checkout 持有者在本機查核 staged、unstaged、未追蹤檔及來源／分支狀態，回報可否安全更新及原因；P2 只觀測，不修改檔案、不送出私人本機路徑或內容。

S15我知道更新將影響哪些決策

由既有Git查核新舊版本，更新前列受影響ADR，含更名／刪除／狀態／取代鏈及既有上層pin；CLI以明確commit讀取，不自行fetch或更新。影響集合無法完整證明時擴大有權scope重讀或停止依賴該判斷的動作。

S16持有 checkout 的 agent 安全更新

checkout持有者在該runtime既有權限內重新核對已配置repo/ref、乾淨、落後且可fast-forward，依D2用既有Git工具自行更新並回報；CLI不執行更新。更新後用CLI按實際新commit重讀；dirty／領先／分岔／遠端未知／來源不符或ref race保留原狀，不reset／stash／靜默切分支，不順便安裝package或部署。

S17 · 延後我讓 host 載入可驗證的新裁示

若日後選配遠端host，由既有獲准維護途徑驗證候選snapshot並切換，失敗留last-good且顯示舊revision／未知。這是延後故事；CLI P1與目前P3不依賴它，D2也不新增host維護或部署權限。

S18更新後我重讀並重檢原交接

每個已納入的runtime在持有者安全更新後回報實際data commit，重新載入／查詢原文與有效判定，code／data checkout與loaded view分開。讀取失敗不把舊view標成新版本；若有last-good明示舊來源，前提變動回原dev2／Spacedock重審。選配host只有在其既有維護完成後另驗，不作本片前提。
S19我把裁示引用交給接手 agent

使用者手動轉交或沿用已驗通路，附傳出者／接手者、原task內容／回合／gate與repo／ADR／commit／digest／core contract版本、freshness及疑義。各接手者須用自己的已授權執行路徑重讀；共用合法owner身分不等於新的裁決權，cloud dot不自動橋接localhost，自動bridge延後。

S20接手者先核對版本與行動範圍

接手者核對自己的runtime／OS/process context及必要gh身分、來源binding與本次行動範圍，再以CLI重讀精確版本；不能繼承另一台機器的gh登入。無路徑／無權／引用不符就回報；ADR、其他agent聲稱或owner帳號不能批准外部動作，也不能代答peer權限提示。

S21我沿用既有任務及驗收入口

以既有 dev2／Spacedock brief、任務與 gate 接手，呈現原 repo／task／執行角色與可核對入口；決策庫僅提供引用，不另造任務狀態或驗收權威。
S22我看到執行與驗收的原始證據

使用者轉交原流程的受保護commit／PR／gate／回執，或用已驗通路讀取；接收者用該runtime既有Git／gh或原入口核對執行者／驗收者／來源版本，證明對應本次任務內容、回合與ADR pin。相同task舊成功／錯回合／舊裁示／無權不能當成本次驗收；CLI不另造台帳。

S23我看出裁示與結果之間的差距

agent在可核對的執行context及已准source binding內，用原任務證據整理預期、實際觀測、未知與影響。CLI讀取裁示不等於能讀敏感執行日誌；證據保留原保護來源，不複製到共用code或把摘要當原驗收。
S24我用新證據重新討論裁示

適用層級原已獲授權的人類決策者，在原可信對話或既有審查來源確認維持或改變；確認綁定可讀原文／diff、來源 repo、層級／scope、精確內容版本及 base，保留可核對的確認出處。agent 整理、Git author 或工程成果不能自行證明上層裁決；內容／base 變更需重新檢視確認。實質改變另立新 ADR，小修留原檔；沿用 dev2 模板、既有配號與確認流程，不把 task amendment 的 Supersedes 當 ADR 欄位。

S25我保留舊裁示與新舊關係

依使用者已確認政策與 dev2 既有機制：實質改變裁示另立 NNNN-short-title.md，沿用原 FO 配號；取代時在舊 ADR Status 使用 Superseded by NNNN，未確認或仍 Proposed 的新稿不提前讓舊裁示失效。不改意思的說明拼字／排版／連結小修留原檔與 Git 歷史，不追改人類原話；舊 Recommended 缺失按 dev2 填 not recorded，不重建當年建議；Legacy 原文保留但不能充當新 required 裁示。分類不明交回原適用決策者，不增設新狀態、欄位或配號權威。

S26我讓受影響的協作者重新確認

使用者確認受影響接手者，逐人手動／已驗通路轉交精確新版本及影響；各runtime以自己的既有權限用CLI讀Git固定commit，核對原文／dev2狀態／保守有效關係，回報版本或受阻原因。無終端／無權來源就待交接，不能以他人轉述冒充重讀；若另採選配MCP／connector則依其實際loaded view核對，不因此新增自動橋接或host權限。

逐片範圍與驗收

P1 · 讀對同一份裁示

已選／Pilot · S01、S02、S04、S10、S11

成果：使用者指定獨立決策repo／ref／commit後，Claude、Codex、dot在各自已授權且可執行CLI的環境，以可核對的身份／來源context讀到同一精確裁示與正確層級，或照實保留疑義。

沿用：沿用既有Git、本機OS/filesystem讀取權限及人類確認；需要GitHub動作才使用該runtime既有gh／Git remote credential。只讀CLI共用查詢core，git／gh負責既有版本／PR動作。尚無已驗可用CLI，最小core整理與封裝是本片新工作；MCP視需要選配。

32–48 active工程小時；風險40–64h；正式fit unknown。四包／五故事對應與限制 · 完整契約草案 · 估工

本片範圍
  • 最小共用查詢core／CLI封裝、受控本機唯讀loader與JSON／人讀輸出、明確錯誤及exit code
  • 獨立repo／ref／commit／原文path／level／scope與正確來源binding
  • 實際OS／filesystem／GitHub或獨立環境的權限邊界；binding拒絕與tenant security分開驗收
  • Claude／Codex／dot在各自真實可執行CLI的已准環境完成讀取；相同owner credential可以協作
  • 可重現的精確原文引用；原生dev2／Legacy狀態與保守effective語義分開呈現
  • code package／core contract、各ADR revision與每runtime loaded view分開標示，固定D0不宣稱最新
本片不做
  • CLI／選配MCP寫入Git、配號、建立task、開PR或merge
  • 自動Git更新、package升級、背景監控或部署
  • 遠端搬站、整庫code／data搬遷、私人ADR公開；最小CLI共用core整理／封裝不屬此排除
  • 新增GitHub帳號／憑證／存取或要求每agent不同GitHub用戶
  • 把help、轉述、合成principal、同OS兩個label／allowlist當成三端或雙使用者隔離通過
  • 修復歷史MCP OAuth、建host／MCP adapter；無終端client的選配路徑另議，不先宣稱可用
依賴／待驗前提
  • 可重用的既有通用查詢core、Git與本機合成多repo測試手段（技術shaping／實作基礎）
    存在可讀generic source與歷史合成測試，但可用CLI／多repo native loader／封裝尚待實作及驗收，不以舊unit當產品證明。
  • 每個client實際可執行CLI且已有source存取權的runtime route（三端端到端驗收條件）
    Codex本機命令／gh metadata可用；dot→已授權delegated local task已有實際shell／Git／gh metadata鏈，不另要求dot前端直接shell，也不推cloud繼承登入。Claude CLI／native reader既有auth及Read/Grep已觀測；正常Claude本人發起唯讀Git命令原回執仍pending（非denied），由我方後續查核。新CLI尚待實作，三端named-client產品回執與合法來源驗收仍未完成。
  • 兩個使用者的實際OS／filesystem／GitHub或獨立執行環境隔離（負向隔離驗收條件）
    macOS兩已知非私密檔的4個read-deny cases已證process限制機制局部可用；不是完整A/B使用者隔離、跨平台保證或AC1通過。完整合成repo harness須限制整個query及Git/helpers，保護foreign metadata／objects／aliases並排除未受限旁路；屬P1驗證工作，不要求使用者先建真帳號或備妥成品。
驗收條件
  • P1-AC1：以實際OS／filesystem／GitHub權限或獨立執行環境分隔的兩個合成使用者及其獨立決策庫，驗證無權context不能取得另一人的索引、原文或source metadata；CLI不新增存取或洩漏拒絕資訊。同OS本來可讀的檔案、兩個label／binding allowlist不能當tenant security證據；測試context尚未定位則明列未驗。
  • P1-AC2：Claude、Codex、dot各自經已授權可執行命令的本機連線task或cloud runtime，實際執行同core／contract CLI查詢同一合成ADR；回傳repo、path、層級／scope、ID、immutable commit、digest與原狀態／effective可對照一致。共用同一合法owner credential可合作；help、轉述、合成principal或另一端gh登入不算本端通過。無可用route的端明列失敗／未驗，不假設cloud繼承本機登入或localhost。
  • P1-AC3：分開的合成上層／工程Git repos各保留實際原文path並配置明確binding，各自回報commit；同號／同key不碰撞，supersession限同來源／層級／scope，工程不能反向覆蓋上層。查詢前依已准context分隔來源；無權／不可讀來源保持未知，不搬原文補齊，未關聯owner的壞來源不污染另一owner。
  • P1-AC4：CLI固定讀D0時，即使來源ref後來到D1仍只宣稱D0，引用可重現原文digest；code package／core／contract、各ADR revision與實際loaded view分開呈現，不把已安裝code、checkout或另一runtime已更新說成全部最新。沒有Git code checkout時照實報package version／不適用。
  • P1-AC5：每個runtime能核對OS/process/environment context及選定source binding；已有clone可依OS/filesystem合法離線讀固定commit，不必每次呼叫gh或取得Sites身份。必要時分別回報實際觀測的gh身分與Git remote credential限制，不假設相同；它們與Sites owner／裁決權分開，共用owner不生成新權威或隔離證明。CLI對未配置binding、錯repo/ref/path／來源不匹配清楚拒絕，不把caller自稱或任意路徑當授權；JSON／人讀模式與error/exit code一致且不新增權限。offline無法觀測遠端身份或freshness時說明未知，不假造遠端最新。
  • P1-AC6：用合成native dev2 docs/adr、Accepted缺Decision key、Legacy與壞鏈／衝突資料，CLI保留原文path／bytes及可讀原狀態；effective無法判定另報unresolved／能力限制，不改Accepted、不強制新欄位或改路徑。JSON與人讀模式對照同一結果，查詢得到unresolved與工具本身失敗分開；致命讀取／驗證錯誤有非零exit與可理解原因，不能以改原文掩蓋。

移除測試：S01固定使用者指定來源與原文路徑；S02證明三端有真實可執行且已授權的路徑；S04分清權威域；S10提供可重現引用；S11保留原狀態與疑義。移除任一就破壞同精確依據或必要權限／裁決邊界。最小core／CLI封裝服務這五故事，不另塞入後片。

P2 · 查明各方版本差異

候選 · S13、S14、S27

成果：接手者分清各runtime的CLI code／ADR checkout與loaded view，知道已配置checkout相對ref的五態、時間及dirty阻礙；選配遠端host只在實際採用時另列。

沿用：沿用P1 CLI精確引用與context；Git提供已准來源的remote／ancestry查核。MCP／Sites不是必要前提；package無Git checkout照實不適用。

本片範圍
  • code／data checkout分role，按repo/ref比對commit與祖先
  • 每runtime loaded view的data revision／digest／時間與所用core分開
  • remote unknown／source mismatch／缺commit／無checkout的誠實回應
  • 本機dirty／分支阻礙唯讀觀測；ADR影響分析留P3
  • 選配host若存在，分開回報其snapshot，無host不阻擋本片
本片不做
  • 修改checkout、reset／stash、loaded view替換或host切換
  • 把Git五態當成已安裝package／contract／部署已更新
  • CLI／MCP根據client自報commit直接修改檔案
  • 未配置來源掃描、登入／新增存取或背景監控
依賴／待驗前提
  • P1（硬依賴）
    已選Pilot但CLI與三端驗收尚未完成；以當時實際證據為準。
  • 各runtime既有Git遠端目標與ancestry觀測權限（查核前提）
    須逐runtime定位；offline／無權／history不足回unknown，不從本機一端權限推定其他端。
  • 選配host的既有唯讀provenance（僅採用遠端adapter時適用）
    不是CLI候選P2的必要依賴，缺此能力只限制該host觀測。
驗收條件
  • P2-AC1：合成 Git 圖逐一顯示一致、落後、領先、分岔；遠端查詢失敗時，即使舊 cache SHA 相等也顯示遠端未知。
  • P2-AC2：一個runtime的loaded view仍D0、data checkout已D1而code checkout一致時，分別回報；另一runtime可不同，不合成全部最新。若採用host另列其revision，不用host有無決定CLI驗收。
  • P2-AC3：repo/ref不符、commit缺失、未配置來源不猜；package無code checkout或某runtime無data checkout顯示不適用，不捏造一致；offline／祖先不足回remote unknown並附時間。
  • P2-AC4：分別準備 staged、unstaged、未追蹤檔與來源／分支不符案例，呈現可理解的阻礙及下一步；前後 Git commit／檔案保持一致，不進行更新或 ADR 影響分析。

移除測試：S13 不在就不知道比較哪個 repo／ref；S14 不在就不知道五態；S27 不在就無法回答本片承諾的本機更新阻礙。三者均直接支撐本片終點。

P3 · 安全對齊並重新讀取

候選 · S15、S16、S18

成果：各runtime持有者依既有Git權限安全更新已配置checkout或保留原狀並說明，再用CLI重讀實際ADR commit與loaded view；不以本片維護遠端host。

沿用：D2由checkout持有者用既有Git工具執行；CLI僅讀固定commit並回報。遠端host維護S17已明示延後，不是本片依賴。

本片範圍
  • 依已准來源的新舊版本列出受影響ADR及上層引用，未知則擴大重讀／停止
  • 乾淨、behind、可fast-forward才由持有者依D2自行更新
  • 各runtime依實際新data commit重讀CLI loaded view，不沿用舊判定
  • 區分更新成功、讀取／驗證失敗與ref race；若有last-good明示舊revision
本片不做
  • dirty強制reset、自動stash、覆蓋領先／分岔或靜默切分支
  • CLI／MCP代做Git更新、package升級或外部動作
  • 遠端host候選切換／部署／MCP維護（S17延後）
  • 自動通知、持續輪詢或新增背景授權
依賴／待驗前提
  • P2（建議順序，非硬依賴）
    可由當次既有Git查核提供必要證據，不要求P2全部code／data／loaded-view診斷產品先交付；替代途徑尚未端到端驗證，無法核實即unknown／停止。
  • P1固定版本讀取，以及各checkout持有者既有Git權限／當次安全查核（不可跳過的能力／證據前提）
    動作前在本runtime重查repo/ref、HEAD／target、ancestry、dirty與ref race，確認D2條件；更新後以CLI核對實際commit並重讀。可沿既有Git完成，不新增權限、不依賴host；不能核實則保留／停止，不宣稱已有端到端替代實證。
驗收條件
  • P3-AC1：agent 查到已配置 repo／ref 的合成 checkout 乾淨、落後且可 fast-forward，重新查核後不逐次等待使用者確認即完成更新；回報來源、操作身分及實際 commit，重讀受影響 ADR 原文與有效判定。
  • P3-AC2：dirty、領先、分岔、遠端未知、來源不符及更新期間 ref 變動時，不覆蓋修改、不自動改支線；以可驗證原因停止依賴該更新的動作。
  • P3-AC3：持有者更新合成data checkout後，CLI重讀並回報實際D1；讀取／驗證失敗不能把D0標D1，若有last-good則明示舊commit／未知。此條驗runtime loaded view，不要求維護遠端host。
  • P3-AC4：一runtime code checkout已更新但installed package或loaded view仍舊，或不同runtime data commit不同，分開呈現；ref在兩次呼叫間移動時重新取得精確引用，不自動安裝／部署。
  • P3-AC5：合成更名、刪除、替代鏈及上層引用變動能進入重讀範圍；既有引用不可讀或不能證明完整時保守擴大為該作用域全部裁示，或停止並回報，不能漏讀後繼續。
  • P3-AC6：每runtime的Git更新與CLI重讀回執標明操作者／context、來源、前後data commit與成功／停止原因；D2不新增host維護、package安裝、部署或背景執行權限。

移除測試：S15界定需重讀的影響；S16由持有者完成安全checkout更新；S18證明CLI loaded view與判定已重讀。移除任一就無法安全重新採用新裁示。S17只服務選配遠端host，非CLI成果必要，留在全圖延後。

沿用：使用者手動轉交引用為本版完整可用路徑；已有通路須另外提出實際可用證據才能取代手動步驟。沿用 dev2／Spacedock 的原任務、brief、gate 及回執，沒有第二份任務系統。

本片範圍
  • 版本固定的跨 agent 交接引用
  • 接手者重讀及本次行動範圍檢查
  • 一次既有 dev2／Spacedock 任務與驗收證據讀回
  • 區分已驗收、失敗、未知與需重新決策
  • 每次交接顯示傳出者、預期接手者、原任務及來源；接手者自行驗證原文和證據權限
  • 原流程回執必須可核對本次任務內容、執行／驗收回合及採用裁示版本
本片不做
  • 自動執行外部動作或由 ADR 補授權
  • 重造任務狀態、gate 或驗收標準
  • 把敏感執行日誌複製進共用 code repo
  • 把每次工程回報自動變成 Accepted 裁示
  • 自動尋找或路由至另一個 agent、跨 agent 橋接、替其他 agent 批准權限提示
  • 以一次遵守政策的觀測，宣稱各 runtime 已有強制保證
依賴／待驗前提
  • P1固定版本讀取（硬依賴）
    接手者須能以自身已准context讀精確來源；P1已選Pilot但未驗收。
  • P2（建議順序，非硬依賴）
    不要求全部版本診斷產品先交付；當次既有Git等能力可提供精確pin與freshness證據，替代路徑未做端到端驗證。
  • P3（建議順序，非硬依賴）
    若無自動更新，可用現有人工核對／更新完成前置，再交接；不得跳過新鮮度未知
  • 共用CLI core與dev2／Spacedock ADR／交接機制相容性（驗收前提）
    需依實際core／contract與dev2版本，用合成native／Legacy資料及原流程證據驗證；歷史MCP／unit證據不代替本片。
  • 使用者手動轉交與接收者各自可讀的原始來源（本版通路契約）
    使用者已選擇此路徑；引用由人轉交，來源存取仍由每位接收者自行驗證。替代通路尚未提出證據時不列可用。
  • 原流程的任務內容／執行及驗收回合／ADR 版本與證據關聯（證據驗收前提）
    需以原 task／gate／回執引用實測關聯；原流程無法提供時保持未知，不另造 task 台帳補猜。
  • 各接手者實際已准的CLI／Git／gh及原證據入口（runtime交接驗收條件）
    不得繼承另一runtime登入；無terminal者的選配MCP／connector須另驗，不能把人工轉述當獨立重讀。
  • 當次精確pin、freshness／適用性、原task範圍與接手者自身讀取權限（不可跳過的能力／證據前提）
    可由當次既有Git與原task來源核對；無法核實則unknown／停止交接，不把人工轉述當獨立重讀，也不因P2未交付跳過查核。
驗收條件
  • P4a-AC1：使用者逐段轉交Claude→Codex→dot合成引用，標傳出者、接手者、原任務、repo/ADR/commit/digest與core contract；接手者以自己已准runtime路徑重讀，回覆context及適用層級。可共用合法owner credential，不以貼文自稱或另一端gh登入當本端權限。
  • P4a-AC2：接手版本已落後或裁示前提改變時，回原任務流程重審；不默默改執行目標。
  • P4a-AC3：合成 ADR 即使寫「部署／發訊」也不能取代本次行動授權；peer 權限提示交回原持有者／使用者，FO 不代答。驗收只宣稱本次觀測與政策符合；未實測的 runtime 強制能力不得標為通過。
  • P4a-AC4：完成一個合成任務並讀回既有流程證據，分清已驗收／失敗／未知；以CLI實際採用core／contract及dev2版本的fixtures比較讀取、原狀態／effective與交接語義。
  • P4a-AC5：使用者轉交原 task／gate／回執引用後，接收者獨立核對執行者、驗收者、提交與結果；無權、失效引用或只有轉述摘要均顯示未知並回報使用者，不擴大權限、不複製受保護日誌。
  • P4a-AC6：同一 task 的舊成功回執、錯驗收回合及引用舊 ADR 的結果，均不能驗收修改後任務；用原流程精確引用核對本次內容、回合、採用裁示與 commit，無法證明關聯就顯示未知。

移除測試：移除精確引用、接手重查、既有任務入口或證據讀回，就不能完成一次可重現的單任務閉環；跨層變動的完整重審另在 P4b。

P4b · 處理跨層衝突並重新裁示

候選 · S05、S06、S24、S26

成果：工程方案引用的上層版本改變或出現衝突時，工程 agent 能呈現影響、交回適用決策者，並把確認後的新版本重新交接。

沿用：沿用P4a人工／已驗通路及原流程；新版本以既有Git修訂／審查與人類確認取得，再用CLI精確重讀，不依賴寫入CLI或MCP。

本片範圍
  • 工程 ADR 固定引用上層版本
  • 跨層矛盾及上層變動的回報
  • 原適用決策者重審
  • 重新交接並由既有任務流程處理範圍變動
  • 沿用 dev2 一決策一檔、原配號與取代狀態；實質變更新 ADR，小修保存原檔
本片不做
  • 由工程 ADR 自動覆蓋總指揮裁示
  • 自然語言矛盾的完備自動判定
  • 工具自動確認新裁示
  • 自動推送或批量重排進行中任務
  • 自動跨 agent 橋接或替其他 agent 回答權限提示
依賴／待驗前提
  • P4a（硬依賴）
    提案中
  • 上層引用及跨層衝突的表達方式（設計前提）
    欄位機制仍為草案；先以引用與人工指明衝突，不宣稱模型能完備辨識矛盾
  • 適用決策者的精確確認及確認後 Git 版本的可讀路徑（人工重審與再交接前提）
    沿用可信確認來源與既有Git提交；各runtime按本端既有權限以CLI讀精確commit。若僅能用選配遠端adapter，按其實際loaded view另驗，讀不到就待交接；不因CLI方向新增host維護或登入授權。D4仍沿用原機制。
驗收條件
  • P4b-AC1：合成工程 ADR 引用總指揮 D0，當 D1 改變適用前提時，呈現原引用與影響；工程 repo 的較新 commit 不自動勝出。
  • P4b-AC2：明示跨層衝突時停止依賴衝突裁示的動作，將問題交回適用決策者；同層替代與跨層引用不混成一條鏈。
  • P4b-AC3：由適用決策者確認維持／改變後，接手者重讀明確版本，原 dev2／Spacedock 流程處理範圍變更；原決策及證據可追溯。
  • P4b-AC4：由使用者將問題與重新確認後的精確版本逐段交回；每位接手者自行核對身分、空間及讀取權限。尚未驗證的自動通路不可作為本片成功前提。
  • P4b-AC5：人類確認綁定 repo、層級／scope、可讀原文／diff、精確內容及 base，可信出處可核對；內容／base 改變重新檢視確認。git author、agent 整理或無權出處不視為裁決；裁示確認不補授權 Git 動作。
  • P4b-AC6：D1已確認後，接手者以本端已准CLI/Git路徑核對原文、明示狀態／有效關係及精確commit；不能證明就待交接。若某端只用選配adapter且loaded view仍D0，明列該端受阻，不視為全體已重讀；使用者確認受影響者，每人版本／原因可核對，不新增自動橋接或host權限。
  • P4b-AC7：合成實質改變經原權威確認後，沿用目標來源 dev2 配號與四章模板形成新 ADR，取代時舊 Status 指向新號且原話／歷史可追。新稿 Proposed 或未確認時不提前切換；只在同層同來源維護取代鏈，工程對上層只固定版本引用。

移除測試：只有單任務交接，無法處理上層方向變更；引用版本、拒絕反向覆蓋、回到原裁決者與重新交接缺一，就不能完成一次跨層重新決策。

P5 · 把確認草案送成受控 PR

候選 · S07、S08、S09、S25

成果：在已配置來源內，使用者確認精確內容、範圍與 base 後，獲准提交者建立一個可審查 PR，回讀 PR 身分與提交內容，證明沒有重複或越權。此片的完成不等待 merge、ADR Accepted 或 host 載入。

沿用：agent沿用既有且本次獲准的git／gh或原Git／PR工具；CLI與選配MCP維持唯讀，不配號或建task。無Git能力由使用者轉交，PR審查／merge仍由原流程；CLI讀取不依賴本片。

本片範圍
  • 本次明確範圍及內容確認
  • 受控草案／PR 與 base commit 衝突檢查
  • 重試可辨識既有結果而非重複 PR
  • 回讀 PR URL／提交版本與 diff，保留確認出處及原文歷史；merge／Accepted／host 載入分開追蹤

本片不做

  • 默示廣泛 repo 寫入、配發憑證或授予外部動作許可
  • 直接改工程 repo 來更新總指揮裁示
  • 覆蓋新的遠端變更或刪除原文歷史
  • 來源設定的變更管理與方案比較介面
  • 把PR建立當成各runtime已重讀或選配host已載入；CLI重讀依實際commit，遠端host維護S17延後或沿既有獲准途徑。

依賴／待驗前提
  • P1來源與精確內容讀取（硬依賴）
    須能辨識已准來源與待提交原文，仍以P1實際驗收證據為準。
  • P2（建議順序，非硬依賴）
    不要求完整code／data／loaded-view診斷產品；可由當次既有Git／PR查核提供base與前次結果證據，尚未端到端驗證此替代路徑。
  • P4a、P4b（建議先完成）
    先驗證跨 agent 如何讀及交接，避免先擴寫入權限
  • 目標 repo 既有 dev2 配號、Git 動作許可與 PR 審查途徑（執行及驗收前提）
    D3/D4不變，D5僅改CLI優先入口；以各runtime現有git/gh及原FO／number guard／審查權限核對本次動作。CLI不另造寫入、配號或任務系統；缺途徑回原權威。
  • 已准來源／base／diff、前次不確定結果與提交前重查（不可跳過的能力／證據前提）
    提交前由持有者用既有Git／PR工具核對本次權限、來源、base、精確diff及可能既有PR／提交；base移動或前次結果不能查明就停止／待確認，不以P2未交付略過。
驗收條件
  • P5-AC1：只對明確確認過的合成 diff、repo、層級、範圍與 base 產生一次可審查 PR；未確認及越權內容拒絕。
  • P5-AC2：送出前 base 已改變則不覆蓋；檢查不確定的前次結果後才重試，不製造重複變更。

  • P5-AC8：合成不改意思的小修留原 ADR，Git 可重現前後版本且原話不被改造；觸及缺 Recommended 的舊檔只按 dev2 記 not recorded。實質語義變更不得包裝小修，分類含糊回原裁決者；不新增 ADR 第五章、YAML 狀態或跨層 supersedes。

移除測試：S07 保存確認依據；S08 綁定本次內容及範圍；S09 建立及回讀唯一 PR；S25 保留原文與新舊關係。移除任一項就無法證明本片提交的是正確、獲准且可追溯的變更。S03 設定管理與 S28 方案比較不影響固定來源內建立 PR，保留在全圖而延後。

九項邊界

  • R1 每位使用者指定獨立決策Git repo；共用code不攜帶私人ADR／憑證。使用者隔離依實際OS／filesystem／GitHub權限或獨立環境驗證，不以label或CLI allowlist冒充tenant security。
  • R2 總指揮裁示與工程 ADR 的權限、適用範圍、來源及裁決者分開；同一引擎不授予同一裁決權。
  • R3 工程 ADR 留在各自 repo，可引用上層決策版本，不能以 supersession 或較新時間覆蓋上層。
  • R4 ADR、Accepted、合併、身分驗證與行動許可是不同事實；OS／process context、gh帳號、Git remote credential、Sites owner與裁決權也分開。agent可沿用同一合法owner身分協作，任務及驗收仍由dev2／Spacedock負責。
  • R5 有效判定保留原文與精確來源；含糊、衝突、無權限或版本不明不能補猜為已生效。
  • R6 版本分code package／core／contract、各ADR repo immutable commit及每runtime loaded view；checkout按已配置repo/ref觀測，選配遠端host另報，不合成全部最新旗標。
  • R7 唯讀CLI不做Git更新或寫入；由checkout持有者依D2用既有Git工具更新。dirty、領先、分岔、遠端未知不覆寫，更新後重讀受影響ADR。
