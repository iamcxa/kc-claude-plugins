## 故事細節

### A1 設定自己的決策空間

| ID／故事 | 設計意圖 |
| --- | --- |
| S01 我指定獨立決策庫與追蹤分支 | 使用者明確指定獨立決策 repo 與追蹤 ref，呈現經驗證的使用者／授權空間及選定來源。工程 ADR 仍在各工程 repo；需要跨層讀取時，把工程 repo 另行明確配置為已有授權的讀取來源，由各 caller 自行驗證存取。不得為了補視圖把工程原文搬進上層庫，工具 code repo 也不是私人 ADR 預設保存地。 來源沿用 dev2 的 docs/adr 或目標 repo 已配置路徑，不要求工程 ADR 改採決策服務的自訂目錄。 |
| S02 我讓三個客戶端讀取同一空間 | Claude、Codex、dot 各自經真實身分驗證進入已授權空間，能查核目前以誰的權限、在哪個空間讀取。客戶端自稱名稱不授予身分或裁決權；未登入及其他使用者不能讀私人資料。 |
| S03 我能改設定而不誤讀別人的庫 | 設定變更須顯示新舊來源差異；來源隔離、可撤銷存取與錯誤設定的拒絕行為可驗證。 |

適用規則：R1、R6

### A2 釐清誰能裁決什麼

| ID／故事 | 設計意圖 |
| --- | --- |
| S04 我分清總指揮裁示與工程決策 | 每筆結果識別層級、scope、來源 repo 與裁決權；跨層資料來自分開且明確配置的授權來源，可分次讀取，每個來源各有自己的 commit。讀不到工程或上層來源就保留未知，不從 project key、時間或另一 repo 的 SHA 推定權限／版本；不承諾跨 repo 原子 snapshot。 |
| S05 我讓工程方案引用上層版本 | 工程 ADR 只在其 repo 適用範圍內決策；固定引用上層 commit／內容摘要，上層變更後可重新評估。 |
| S06 遇到跨層衝突時我請原裁決者處理 | 不能把兩層替代鏈合成一條；工程端提出衝突及影響，回到上層決策者，不自動反向覆蓋。 |

適用規則：R2、R3、R4

### A3 討論並確認裁示

| ID／故事 | 設計意圖 |
| --- | --- |
| S07 我保留原話與決策出處 | 保留人類原話、作者／裁決者與可信出處，並區分引用、agent 整理與人類確認；PR 提交前可核對草案未冒稱新的確認。 |
| S28 我比較可選方案再形成草案 | 討論階段整理可選方案、取捨與建議，供適用決策者選擇；在內容已確認後提交 PR 的切片中，不為此另建方案比較介面。 |
| S08 我確認特定版本的裁示 | 適用層級原已獲授權的人類決策者確認可閱讀的精確原文／diff、repo、層級／scope、內容版本及 base；保留可核對的可信對話或既有審查出處。內容／base 改變需重新檢視確認，無法核對則待確認；確認裁示內容、本次 Git 動作許可、PR／merge／Accepted 與 host 已載入分別核對。 |
| S09 我把草案送成可審查的變更 | agent 透過既有 Git／PR 工具，只對已配置且本次獲准的 repo 與範圍建立可審變更，保留 base、差異、確認出處及原文歷史。沒有 Git 權限的客戶端由使用者轉交給有既有權限的提交者；MCP 維持唯讀，host 代寫延後。 新決策草案先不取號；需要新 ADR 時沿用目標 repo 的既有 dev2 FO／number guards 配號及審查，一個新裁示一個新號。無該途徑就回原權威，不由 MCP 或 agent 另造配號服務。 |

適用規則：R2、R4、R5、R9

### A4 查出此刻適用的決策

| ID／故事 | 設計意圖 |
| --- | --- |
| S10 我查到原文與可重現的版本引用 | 回應能回到經授權的當前使用者／空間，以及來源 repo、層級／範圍、完整 ADR ID、path、commit 與內容摘要。身分與來源不可混淆，錯誤不洩漏其他人的庫或資料是否存在。 |
| S11 我知道哪些已生效或仍有疑義 | 照實顯示 dev2 原始 Proposed／Accepted／Deprecated／Superseded by NNNN 狀態。取代沿舊 ADR 的明示目標，只在同來源／層級／適用範圍內解析；不從較新日期或編號推論。既有服務的 Decision key／resolved／unresolved 是保守查詢擴充，不是新 ADR 格式或狀態：缺 key、壞鏈、衝突或來源疑義時保留未知，並與原 Accepted 分開呈現，不強制改寫原文或新造欄位。 |
| S12 我分清查不到與沒有讀取權限 | 使用者得到可行的下一步，但對外錯誤不洩漏不該讀的 ADR 或 repo 是否存在。 |

適用規則：R2、R3、R4、R5、R9

### A5 對齊手上的版本

| ID／故事 | 設計意圖 |
| --- | --- |
| S13 我知道目前比的是哪個來源 | 分別列出 host 決策來源與 agent 的已配置 checkout；checkout 可以是工具 code 或工程 repo，讀 MCP 不強迫 clone 私人決策庫。 |
| S14 我看懂一致落後領先分岔或未知 | 相同 repo／ref、完整 commit 與祖先證據才能判定；觀測時間及遠端未知原因可見，不能把舊 tracking ref 當最新。 |
| S27 我知道更新被哪些本機狀態阻擋 | 先由 checkout 持有者在本機查核 staged、unstaged、未追蹤檔及來源／分支狀態，回報可否安全更新及原因；P2 只觀測，不修改檔案、不送出私人本機路徑或內容。 |
| S15 我知道更新將影響哪些決策 | 更新前列出精確新舊版本差異與受影響 ADR，含更名、刪除、狀態／替代鏈及已存在的上層引用；無法證明影響集合完整時保守擴大重讀範圍或停止依賴該判斷的更新。 |
| S16 持有 checkout 的 agent 安全更新 | checkout 持有者在既有本機權限內重新核對已配置 repo／ref、工作目錄乾淨、落後且可 fast-forward 後，自行更新，不逐次等待確認。更新後回報來源與實際 commit，重讀受影響 ADR；dirty、領先、分岔、遠端未知、來源不符或查核期間 ref 改變均保留原狀並回報，不強制 reset、不自動 stash 或切分支。 |
| S17 我讓 host 載入可驗證的新裁示 | host 維護者／agent 依既有獲准維護途徑讀配置來源、驗證並切換 snapshot，回報操作身分、授權空間／來源與新 revision；失敗保留 last-good 並顯示落後／未知。checkout 自動更新規則不新增 host 維護權限，也不是叫客戶端替 host checkout。 |
| S18 更新後我重讀並重檢原交接 | 兩邊各自回報新 commit；受影響 ADR 原文與有效判定重新讀取；若適用前提變動，既有任務回原流程重新裁示。 |

適用規則：R5、R6、R7

| ID／故事 | 設計意圖 |
| --- | --- |
| S24 我用新證據重新討論裁示 | 適用層級原已獲授權的人類決策者，在原可信對話或既有審查來源確認維持或改變；確認綁定可讀原文／diff、來源 repo、層級／scope、精確內容版本及 base，保留可核對的確認出處。agent 整理、Git author 或工程成果不能自行證明上層裁決；內容／base 變更需重新檢視確認。實質改變另立新 ADR，小修留原檔；沿用 dev2 模板、既有配號與確認流程，不把 task amendment 的 Supersedes 當 ADR 欄位。 |

## 已確認的邊界

- R1：每位使用者明確指定獨立決策 Git repo；共用工具 code 不攜帶私人 ADR、身分或憑證。
- R2：總指揮裁示與工程 ADR 的權限、適用範圍、來源及裁決者分開；同一引擎不授予同一裁決權。
- R3：工程 ADR 留在各自 repo，可引用上層決策版本，不能以 supersession 或較新時間覆蓋上層。
- R4：ADR、Accepted、合併、身分驗證與行動許可是不同事實；任務及驗收權威沿用 dev2／Spacedock。
- R5：有效判定保留原文與精確來源；含糊、衝突、無權限或版本不明不能補猜為已生效。
- R6：新鮮度按配置的 repo 與追蹤 ref 比較 commit；host 決策 snapshot、agent checkout、部署 code 分別描述。
- R7：有未提交修改不可強制 reset；領先、分岔、遠端未知不得自動覆蓋；更新後重讀受影響 ADR。
- R8：來源隔離與機敏資料留在原保護來源；公開案例使用合成資料。裁示、讀取權限與本次外部動作授權分開核對，提交、merge、部署、host 維護及新增存取須有各自適用授權。
- R9：ADR 沿用 dev2 格式與配號；實質變更新檔，小修留原檔，原話及歷史不改寫。
