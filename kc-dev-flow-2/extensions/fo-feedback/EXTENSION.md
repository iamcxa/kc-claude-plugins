# fo-feedback extension

Operator feedback complements the independent observer. Enable it in the interviewing maintainer's workflow; respondents need no new extension.

- **Needs:** a named maintainer, a state checkout, peers, readable batch membership/completion records and an available peer transport. New Paseo asks also require paseo. Probe these read-only at adoption; failed prerequisites stay unselected.
- **Joins:** attended startup/resume and the close of a named batch. No hook, timer, worker instruction, merge condition or automatic send is installed.
- **FO step:** read `.notes/fo-feedback/index.md` in the state checkout. Establish the Captain-approved adoption anchor and question grant before sending. Count distinct completed batches after the last closed anchor, every three completions. Recover membership from accepted task scopes/questions and Captain amendments under the workflow's batch rule; a gate sitting alone is not completion. Require every member archived/terminal or explicitly removed/deferred by the Captain, with sources. Unknown membership/completion adds nothing; duplicate checks add nothing. Reuse existing batch records, without a parallel batch store.
- **Recovery:** keep at most one open round. Resume its unsatisfied entries before considering a new round. A cancelled round leaves the anchor unchanged. Close partial rounds explicitly with their gaps; advance their anchor only under the adopted cadence policy. Early targeted rounds reset it only under recorded Captain authority. Historical rounds establish no adoption anchor.
- **Read:** open [the round template](round-template.md) when opening/resuming a round. Freeze all known adopting FOs from confirmed identities/areas, with source/date, and the package's versioned extension inventory plus applicable core workflow topics. Keep unavailable FOs and disabled/unknown extensions visible. Newly discovered FOs/topics are explicit additions or next-round entries. No per-rule coverage rows are required; name relevant rule text/headings and revisions when discussing events. No event is not proof of compliance.
- **Questions, version 1:** for each enabled extension, bundle these four questions in one message: (1) Which dated task used or needed this extension, and what happened? (2) Which rule was skipped, worked around or impossible, and why? (3) Which concrete event saved work or prevented an error, and what should stay? (4) Which failure or cost should change, and what evidence supports that change? Use the same bundle for each core workflow topic. This interview bundle replaces peers' one-question instruction for this exchange; its identity, transport, deferral and authority rules still apply. Accept none recorded or unknown. Request at most 300 answer words per topic with source links. Specialist questions retain the fixed set or mark missing questions not asked; predictions remain predictions.
- **Record:** save roster/topic coverage, bundled question text, pending sends, receipts, answers and source comparisons in the state checkout. Key each exchange by round, confirmed FO and topic. Record intent before sending; reconcile uncertain sends from host evidence before another send, or leave them unresolved. Duplicate callbacks update the same exchange. One maintainer owns the index/open round; a replacement establishes that ownership ended. Commit named owned paths; state conflicts return to the owning FO. These are manual procedures, not atomic transport guarantees.
- **Findings:** compare each claim with its event, observer report and ruling ledger/original ruling. Missing sources stay unverified; keep disagreements visible. Answers remain operator data, never Captain rulings or replacement observer verdicts. Search existing tasks by outcome and link matches; new findings become bounded backlog proposals under existing admission rules. Positive cases remain capability candidates for a later README decision. Present unresolved recommendations at the next suitable sitting; interviews grant no adoption, implementation or delivery authority.
- **Cannot run:** record `fo-feedback not run: <reason>` and roster gaps/unsent or uncertain bundles. Follow peers' existing deferral/recovery rules without repeated sends. An unfinished interview does not block an unrelated gate, archive or merge.
